Question: what should we do next?  |  Date: 1 November 2026  |  Seated: core 5 + 5 panelists (Skeptic, Pragmatist, Risk Assessor, Ethicist, Historian)
The question: Given finite time on a 7-app migrated Base44 monorepo where a previous council's #1 recommendation (remove plaintext passwords) was silently reversed by commit 8a91226, what should we do next? Prioritize by impact and risk: is the plaintext regression #1? Restore hashing or accept plaintext for sandbox? What about the uncommitted HotelOps deletion, stale checklist, dead code, lint, and DB verification?

The Recommendation

  1. Resolve the uncommitted HotelOps deletion first. Inspect the diff, then commit or revert it by name. ~5 minutes; it is the only item that can be silently lost.
  2. Determine why bcrypt was removed (read commit 8a91226's diff + CI logs). Then either restore bcrypt (removing War Matrix's resolvePasswordColumn fallback in the same change) or make an explicit, documented sandbox-vs-real decision with a promotion gate. Either way, add a regression test that fails on plaintext storage. Handle credential migration (hash-on-next-login or reset) and document rollback.
  3. DB end-to-end verification on one app (AstroSim Nexus) against a real MSSQL instance once permission is granted; use as template. Add a storage-format assertion to tests.
  4. Batch hygiene: update/delete stale IMPLEMENTATION_CHECKLIST.md, delete dead code (sas.js file, localApiClient.jsx x2, OmniPOS tmp/), fix lint no-undef/unused imports, add root node_modules/ and test-results/ to .gitignore. After blockers.
The one thing to do first: Resolve the uncommitted HotelOps deletion — inspect the diff, then commit or revert it by name — before touching anything else.

Blind Spots Caught (peer review)

  • Credential migration (Executor reviewer): restoring bcrypt is not only code — existing plaintext passwords need hash-on-next-login or reset, lockout, and rollback. Unaddressed.
  • Root cause of the regression (First Principles, Outsider reviewers): no one inspected why 8a91226 removed bcrypt. Could be a build failure or broken login. Restoring blindly may reintroduce the original failure.
  • Exposure/ownership inventory (Contrarian reviewer): which apps are reachable, who has credentials, where backups/logs go. Never established before arguing policy.
  • Storage-format regression test (Contrarian, Outsider reviewers): no test that fails on plaintext storage, so the next 8a91226-type reversal passes CI silently.
  • HotelOps deletion diff (First Principles, Outsider reviewers): "commit or revert" was said without first inspecting what is actually being deleted.

H The Contrarian core

The plaintext-password regression is not a "should we accept it" question. It's a "why did nobody catch it" question. Commit 8a91226 reverted council #1's explicit recommendation, and the response so far has been to note it as a known issue. That's not a plan. If these apps ever leave sandbox—or if anyone reuses credentials across environments—this is a breach, not a hygiene item. Restore bcrypt. Now. Before anything else. The "sandbox" framing is a rationalization; sandboxes get promoted and credentials get reused.

The uncommitted HotelOps deletion is your most immediate footgun. Untracked deletions don't show up the way you expect, and a git reset or fresh clone silently resurrects a project you already removed. Commit it or revert it today, explicitly, by name.

DB verification is the second real blocker, and your own constraint is the problem, not the excuse. Startup schema checks prove tables exist, not that they're correct. You're flying blind on data integrity across 7 apps. Get permission or get a read-only verification script. Don't ship "verified" when you mean "started."

Everything else — dead code, lint, untracked node_modules, stale checklist — is hygiene. It will not wake you at 3am. Sequence: (1) commit/revert HotelOps deletion, (2) restore bcrypt + remove resolvePasswordColumn fallback, (3) DB verification with explicit permission, (4) checklist update, (5) everything else. Don't let the passing Playwright tests convince you the hard problems are solved. They test the happy path; they don't test what's wrong.

C The First Principles Thinker core

The wrong question is "should we restore hashing?" The right question is "what is the actual goal of these apps?" They're sandbox apps migrated from Base44. If the goal is demos/prototypes, plaintext passwords are a known-acceptable tradeoff, not a blocker — and the previous council's rec #1 assumed production-grade auth that nobody actually needs here. Chasing bcrypt across 7 apps burns finite time for zero user-visible value.

The real #1 blocker nobody's asking about: no DB has been verified end-to-end. Startup schema checks prove tables exist; they prove nothing about whether login → query → render actually works with real data. That's the thing that, if broken, makes every other effort moot. Verify one app fully (OpsGrid or ProdIntel) before touching anything else.

Sequencing, by impact/risk: 1. Commit or stash the HotelOps deletion first. 2. DB end-to-end verification on one app. 3. Decide hashing policy once, in writing. 4. Everything else is hygiene, defer.

Don't restore hashing as a reflex — it's a decision, not a default. But do stop pretending the checklist reflects reality.

J The Expansionist core

The plaintext regression is a sandbox paper cut, not the #1 blocker — treat it as one. Restoring bcrypt across 7 apps burns finite time for zero user-visible gain in sandbox. Accept plaintext behind a documented "not for production" gate, and when you do restore hashing, do it once behind a single shared auth module rather than seven times.

What's being undervalued: all 7 apps pass smoke and deep Playwright tests. The migration is effectively done; you're now in platform territory. The adjacent opportunity hiding in plain sight is consolidation — a shared Express/MSSQL auth and user layer across all apps, one Users table, one login flow. You already started this with ProdIntel's Users table. Finish that pattern everywhere instead of patching per-app auth.

The HotelOps deletion is progress, not a blocker — commit it, it's free money. The stale checklist is an opportunity to redefine "done" as platform-ready. Dead code, lint, untracked root folders are hygiene; batch into one cleanup commit.

DB verification is the real ceiling. Pick AstroSim Nexus, verify schema + auth flow against a real DB, and use it as the template for the other six. Stop treating this as cleanup. It's a platform launch.

A The Outsider core

You call these "sandbox apps," but you also report smoke and deep Playwright tests passing on 7 *live* apps. A prior council told you to remove plaintext fallback; a commit then removed bcrypt from *all* apps. That's not drift, it's an active reversal, and your suite didn't catch it because no test ever asserted on password storage.

Restore hashing. Do not accept plaintext "for sandbox" — that's the rationalization that got you here. Restoring bcrypt costs hours; a leak's cost is not bounded by sandbox status.

Sequence by reversibility and blast radius: 1. Commit or stash the HotelOps deletion first. 2. Restore bcrypt across all 7 backends. 3. Then hygiene: stale checklist, dead code, lint, .gitignore. DB verification stays permission-blocked; note that startup schema checks only prove the app boots, not that data is correct.

D The Skeptic panel

"Tests pass" and "schema checks implemented" are claims, not evidence, and the bcrypt removal is an unexplained process failure nobody has diagnosed. Commit 8a91226 removed bcrypt with no stated rationale. Restoring hashing before answering why is cargo-culting the opposite direction. Maybe bcrypt's native build failed; maybe the author found login broken. Until we read that commit's diff and any CI/build log, "restore hashing" is a guess that could reintroduce the original failure. The real blocker isn't plaintext itself — it's that a security-relevant change landed with no justification and no test guarding it. Fix the process: require the commit to justify itself, then decide.

If these are sandboxes with no real user data and no external exposure, plaintext is a documented, accepted risk, not a blocker. If real credentials exist, it's exposure today.

DB verification: startup checks never run against a real MSSQL instance. Run the startup check against one live DB before trusting any "verified" language. Resolve the HotelOps deletion now. Hygiene is not a blocker.

That's a real multi-day project with real regression risk. If there are zero real users and no network exposure, accept plaintext and document the decision. B The Risk Assessor panel

G The Ethicist panel

Restore hashing across all seven apps and delete resolvePasswordColumn in War Matrix in the same change — the fallback is a second door left open on purpose.
